# Agent设计模式浅析系列 (一) - ReAct：Agent 不是会回答，而是会边想边干

最近我想系统写一组 Agent 设计模式。

不是那种把名词摊开讲一遍的系列，而是想把这些模式放回真实工程里看：它到底解决什么问题，为什么会变成现在很多 Agent 框架的底层范式，用起来又会在哪些地方翻车。

这个系列我暂时叫「Agent 设计模式」。

后面会依次聊 ReAct、Routing、Plan-and-Execute、Reflection、Evaluator-Optimizer、Orchestrator-Worker、Parallelization、Blackboard、State Machine、Graph-based Agent、Memory-Augmented Agent 这些东西。

每篇只讲一个模式。

尽量不堆概念，而是把它讲成一个工程师真的会用到的工作方法。

第一篇先讲 ReAct。

这个词很多人都见过，Reason + Act，翻译过来就是「推理 + 行动」。

听起来很简单，甚至有点像废话。

Agent 不就是先想一下，再调用工具吗？

但我越看越觉得，ReAct 其实是 Agent 从「聊天机器人」变成「干活系统」的第一道门槛。

因为它真正改变的不是提示词格式，而是模型和世界的关系。

以前模型回答问题，基本是在脑子里硬想。

你问它一个事实，它靠参数记忆猜；你让它分析一个项目，它靠上下文里那点文件片段推；你让它排查一个 Bug，它可能先编一个很像真的原因。

看起来很聪明，但有一个致命问题：

它没有办法确认自己是不是看错了。

ReAct 的思路就朴素很多。

不知道就去查。

查完再想。

想完再决定下一步要不要继续查。

## ReAct 到底在干什么

ReAct 最早来自 2022 年那篇论文《ReAct: Synergizing Reasoning and Acting in Language Models》。

论文里有个核心想法：不要把「思考」和「行动」拆成两个孤立能力，而是让模型在一个轨迹里交替生成 reasoning traces 和 actions。

直白点来说就是：

模型不是一口气把答案憋出来，而是一边写下自己当前的判断，一边调用外部工具，然后根据工具返回结果更新判断。

大概长这样：

```
用户问题→ Thought：我现在需要确认什么？→ Action：调用搜索、数据库、文件读取、浏览器、API→ Observation：工具返回了什么？→ Thought：这些信息够不够？有没有矛盾？→ Action：继续查，或者执行下一步→ Final Answer：给出最终结果
```

这个循环里最关键的不是 Thought。

很多人一看到 ReAct，就盯着「思考链」看，觉得重点是让模型把推理写出来。

我觉得这只说对了一半。

ReAct 真正厉害的地方，是 Observation。

也就是工具返回的外部事实。

没有 Observation，Thought 很容易变成自言自语。模型越写越顺，越顺越像真的，最后把自己也骗了。

有了 Observation，模型每走一步都要被现实敲一下。

搜索结果不对，就改方向。

测试报错了，就换假设。

数据库查不到，就承认没有数据。

这就是 ReAct 和普通 Chain-of-Thought 最大的区别。

CoT 更像一个人在白板前推理。

ReAct 更像一个工程师坐在电脑前排查问题：脑子里有假设，手上会跑命令，看到结果之后再调整。

## 为什么 Agent 需要这个循环

我以前看很多 Agent Demo，有一种很熟悉的割裂感。

页面很酷，动画很多，模型也会说「我正在分析你的需求」。

但真正让它做事的时候，它经常像一个刚入职但特别自信的实习生。

它会直接下结论，在没有查接口文档的情况下，开始写一段看起来很标准的调用代码。

这不是模型坏，这是流程不对。

如果一个 Agent 只能生成答案，它就只能在语言空间里工作。

但真实任务大多不在语言空间里。

代码在仓库里。

订单在数据库里。

网页按钮在浏览器里。

错误信息在日志里。

用户真正要的也不是「你觉得应该怎么做」，而是「你看过现场之后，真的把事办了」。

## 举个代码调试的例子

假设用户说：

「这个登录页提交之后一直 500，帮我看看。」

一个没有 ReAct 的模型，很可能会直接开始猜：

可能是 token 过期，可能是后端参数校验，可能是数据库连接。

这些都可能对。

但也都可能是废话。

一个 ReAct Agent 的路径应该更像这样：

```
Thought：我要先确认 500 来自前端请求还是后端接口。Action：查看浏览器 Network / 读取服务端日志Observation：POST /api/login 返回 500，日志里提示 users 表缺少 last_login_at 字段Thought：这不像鉴权问题，更像数据库迁移没跑。Action：查看 migration 文件和当前 schemaObservation：migration 里新增了 last_login_at，但测试环境数据库没应用Thought：根因比较明确了，需要跑迁移或兼容旧字段。Action：执行迁移 / 修改代码防御Observation：接口恢复 200Final Answer：说明根因、改了什么、怎么验证
```

先形成一个小假设。

再拿工具验证。

验证结果推翻或加强假设。

然后继续下一步。

这就是 ReAct 最适合的场景：搜索问答、代码调试、文件分析、浏览器自动化、数据查询、运维排障。

只要任务需要外部信息，而且信息会影响下一步动作，ReAct 就有价值。

## ReAct 解决的不是智商问题

很多人会误解 Agent。

以为模型更强了，Agent 就自然更强，我认为不完全是这样的。

模型能力当然重要，但 Agent 的可靠性，很多时候不是智商问题，而是工作流问题。

一个很强的模型，如果被要求一次性回答，它还是会因为上下文不全而胡说。

一个没那么强的模型，如果被放进好的 ReAct 循环里，至少会知道什么时候该查、查什么、查完怎么修正。

论文里的 ReAct 在 HotpotQA、FEVER 这类问答和事实验证任务里，就是靠和 Wikipedia API 交互，缓解纯推理容易幻觉、错误一路传播的问题。

这点放到今天的工程 Agent 里依然成立。

你让模型生成 SQL，它可能写错字段。

但如果它能先查 schema，再写 SQL，再执行 dry run，再根据错误修正，成功率会完全不一样。

你让模型改代码，它可能漏掉调用方。

但如果它能先搜索引用，再改实现，再跑测试，再根据失败日志继续改，它就不再是单轮生成器，而是一个闭环系统。

这里面有个很有意思的变化。

模型不再只是「输出答案」。

它开始管理自己的不确定性。

不知道就查。

不确定就验证。

错了就根据反馈回到循环里。

这才是 Agent 的味道。

## 但 ReAct 也不是万能钥匙

说到这里，ReAct 好像很完美。

其实不是。

它的问题也很明显。

第一个问题是成本。

ReAct 是循环，不是单次调用。

每一次 Thought、Action、Observation 都要消耗上下文和工具调用。任务一复杂，很容易跑出十几步，Token 和时间都上去了。

所以生产里不能让 Agent 无限想、无限查。

必须有步数上限、超时机制、预算控制。

第二个问题是工具选择。

模型不是天然知道该用哪个工具。

工具描述写得含糊，它就会乱选。

搜索能解决的事，它可能去读数据库。

文件里有答案，它可能跑去联网查。

所以 ReAct 的工程重点，不只是 prompt 里写一句「你可以使用工具」，而是把工具边界、输入输出、失败情况都设计清楚。

第三个问题是 Thought 不一定要暴露给用户。

很多早期 ReAct 示例会把 Thought 直接展示出来。

这在研究里有解释性，在产品里不一定合适。

真实系统里，更常见的做法是：内部保留推理和工具轨迹，用户只看到简洁的进度和最终结论。

不然用户会看到一大堆半成品想法，体验很吵，而且有安全和隐私风险。

第四个问题是它容易陷入循环。

比如搜索结果不够好，它继续搜。

测试失败了，它继续改。

改完又失败，又继续改。

如果没有明确的停止条件，Agent 会很像一个钻进洞里的自动化脚本，越跑越远。

所以一个好用的 ReAct Agent，一定要有退出机制：

什么时候认为信息足够。

什么时候承认做不了。

什么时候把选择权交还给人。

这三个问题不解决，ReAct 很容易从「会干活」变成「会忙活」。

## 工程上怎么实现

如果自己实现一个最小 ReAct Agent，其实不复杂。

核心只需要四个东西。

第一，消息状态。

你要保存用户目标、已经做过的动作、工具返回结果、当前中间结论。

第二，工具注册表。

每个工具要有名称、用途、参数 schema、返回格式、错误格式。

第三，循环控制器。

它负责把当前状态交给模型，让模型选择下一步是调用工具还是结束。

第四，观察结果写回。

工具执行之后，不要只把结果丢给用户，而是写回 Agent 的上下文，让下一轮推理能看到。

伪代码差不多这样：

```
state = [user_task]
for step in range(max_steps):
    decision = model.next(state, tools)
    if decision.type == "final":
        return decision.answer
    result = run_tool(decision.tool, decision.args)
    state.append({
        "action": decision,
        "observation": result,
    })
return "信息还不够，我先停在这里。"
```

真正麻烦的是旁边那些看起来不酷的东西：

工具权限怎么控。

失败怎么重试。

敏感操作要不要二次确认。

上下文太长怎么压缩。

工具返回太脏怎么清洗。

这些东西才决定 ReAct 能不能进生产。

## 我对 ReAct 的理解

如果只用一句话总结 ReAct，我会这么说：

它让模型从「一次性表达观点」，变成「持续根据现实修正自己」。

这个变化很小，也很大。

小到它只是一个循环：

想一下，做一下，看结果，再想一下。

大到它几乎定义了今天很多 Agent 的基本行为方式。

不管你后面用的是 Plan-and-Execute、Reflection、Multi-Agent，还是 LangGraph 这种图编排，里面经常都会藏着 ReAct 的影子。

因为再复杂的 Agent，最后都绕不开这个基本问题：

下一步该做什么？

做完看到了什么？

看到之后要不要改主意？

ReAct 不是最复杂的 Agent 模式。

但它可能是最值得先理解的一个。

因为你一旦理解了它，就会发现很多 Agent Demo 到底是在真干活，还是只是在把回答包装得更像干活。

真正的 Agent，不是会说「我正在处理」。

而是会在不确定的时候停下来，看一眼世界，然后再继续。

这才是思考行动模式最朴素、也最有价值的地方。

下一篇我准备写 Routing / 路由分发模式。

ReAct 解决的是一个 Agent 怎么边想边做。

Routing 解决的是另一个问题：

当任务不是一种类型时，谁来决定把它交给谁。

这个系列大概会按两条线往下写。

一条是单 Agent 自己怎么变可靠，比如 ReAct、Plan-and-Execute、Reflection。

另一条是多个流程或多个 Agent 怎么协作，比如 Routing、Orchestrator-Worker、Blackboard、State Machine。

如果说 ReAct 是让 Agent 学会「边想边干」，那后面的模式，就是继续解决一个更现实的问题：

当任务越来越复杂，怎么让 Agent 不只是聪明一会儿，而是稳定地把事情做完。
