# Agent设计模式浅析系列 (三) ：Plan-and-Execute - 别让 Agent 一步一步瞎走

这是「Agent 设计模式」系列的第三篇。

第一篇讲 ReAct，让 Agent 学会边想边干。

第二篇讲 Routing，让任务先走到合适的通道里。

这一篇讲 Plan-and-Execute。

它解决的是一个很现实的问题：

Agent 做复杂任务的时候，很容易只顾眼前一步。

这件事我在 AI Coding 里见过太多次。

你让 Agent 帮你重构一个模块。

它先改一个文件。

改完发现类型报错。

再修另一个文件。

修完发现测试挂了。

又去补一个兼容逻辑。

最后整个任务确实一直在推进，但你看着它跑，会有一种不太踏实的感觉：

它好像很忙，但不一定知道自己要去哪。

Plan-and-Execute 就是为了解决这个问题。

先别急着动手。

先把计划写出来。

然后再逐步执行。

## 它和 ReAct 有什么区别

ReAct 的节奏是：

```
想一步做一步看结果再想下一步
```

Plan-and-Execute 的节奏是：

```
先生成整体计划再逐步执行计划必要时重新规划
```

LangChain 早期介绍 Plan-and-Execute agent 时，也把它拿来和 ReAct 风格的 Action Agent 对比。

ReAct 更像一个人边走边问路。

Plan-and-Execute 更像先打开地图，定出几段路线，然后每走完一段再看要不要调整。

这不是说 Plan-and-Execute 一定比 ReAct 高级。

它只是适合另一类任务。

如果问题很短，下一步高度依赖工具观察，ReAct 很好。

比如查一个接口报错、搜索一个事实、读一个文件。

但如果任务本身有明显阶段，步骤之间还有依赖关系，Plan-and-Execute 会更稳。

比如：

- 代码迁移
- 长文调研
- 竞品分析
- 数据清洗
- 旅行规划
- 多文件重构

这些任务如果只靠 ReAct，一步一步临场发挥，很容易走偏。

## 计划到底有什么用

很多人对「先写计划」有点抵触。

感觉像流程主义。

尤其是模型这么强了，为什么不能直接干？

问题是，复杂任务最怕的不是慢。

最怕的是局部正确、整体错误。

比如你让 Agent 写一篇深度分析。

它可能第一段写得很好，第二段也挺顺，第三段开始展开一个旁支，最后文章偏题了。

比如你让 Agent 迁移一个 API。

它可能先改调用方，再改类型，再补测试，但忘了文档、脚本、配置和兼容层。

每一步看起来都合理。

放在一起就是漏。

计划的作用，是先把任务的轮廓摊开。

让模型不要只看脚下这块砖。

它要先回答：

要完成这个任务，需要哪几步？

哪些步骤有先后关系？

哪些地方需要验证？

哪些地方可能要回滚或重新规划？

这就是 Plan-and-Execute 的价值。

它不是让 Agent 变得更聪明。

它是让 Agent 不那么容易失去全局感。

## 一个代码迁移的例子

假设你有个项目，要把旧的 `UserService.getUser(id)` 迁移成新的 `UserRepository.findById(id)`。

一个直接行动的 Agent 可能会这么做：

先搜 `getUser`。

改一个文件。

跑测试。

修报错。

再搜下一个。

这也能做。

但如果项目稍微大一点，它很容易漏掉隐藏调用、测试 mock、文档示例、脚本里的使用。

Plan-and-Execute 的路径会更像这样：

```
Planner：
1. 搜索所有 getUser 调用点
2. 区分生产代码、测试代码、文档和脚本
3. 先迁移核心业务代码
4. 再迁移测试 mock 和 fixture
5. 更新文档示例
6. 运行相关测试
7. 根据失败结果重新检查遗漏点

Executor：
逐步执行每一步，并把结果写回计划状态
```

这个过程看起来慢一点。

但它有两个好处。

第一，任务不容易漏。

第二，执行中途更容易知道自己在哪。

如果第 4 步测试 mock 迁移失败，Agent 不会以为整个任务已经乱了。

它知道自己卡在计划里的哪一段。

这点在长任务里非常重要。

## Planner 和 Executor 最好分开

Plan-and-Execute 的核心，是把「规划」和「执行」拆开。

这两件事看起来都可以让同一个模型做。

但它们需要的能力不一样。

Planner 要擅长全局拆解。

它要看到任务边界、依赖关系、风险点和验证方法。

Executor 要擅长局部完成。

它要读文件、调工具、执行命令、处理错误。

在工程上，这两个角色甚至可以用不同模型。

复杂规划用更强模型。

具体执行用便宜一点、快一点的模型。

LangGraph 的一些 Plan-and-Execute 方案里，也强调过这个优势：大模型不必每一步都参与，子任务可以交给更小的模型或固定工具链处理。

这就是它和 ReAct 的成本结构差异。

ReAct 往往每一步都要回到同一个大脑。

Plan-and-Execute 可以让大脑先定方向，然后让手去干活。

当然，这里有个前提：

计划要能被执行器理解。

如果 Planner 写出来的是「优化代码结构」「提升用户体验」「完善测试覆盖」这种空话，Executor 还是会懵。

一个好计划应该像任务清单，而不是愿景口号。

## 什么时候需要重新规划

Plan-and-Execute 不是一次性计划到底。

真实任务里，计划经常会错。

文件结构和想象不一样。

数据质量比预期差。

API 文档过期。

测试暴露了隐藏依赖。

这时候不能死守原计划。

所以 Plan-and-Execute 里通常要有 Re-plan。

也就是执行到某一步之后，根据新信息更新计划。

```
原计划：
1. 调接口拿数据
2. 清洗字段
3. 生成报表

执行发现：接口返回缺少关键字段

新计划：
1. 查备用数据源
2. 合并两份数据
3. 标记缺失字段
4. 再生成报表
```

这里最容易出问题的是两个极端。

一个是永不重新规划。

计划错了也硬走，最后走到死胡同。

另一个是频繁重新规划。

每遇到一点小阻碍就推翻计划，最后一直在写计划，不干正事。

比较好的做法，是给 Re-plan 设条件。

比如：

- 关键依赖不存在。
- 连续两次执行失败。
- 发现新约束会影响多个后续步骤。
- 用户改变目标。

这时候才触发重新规划。

否则就继续执行当前计划。

## 它不适合什么场景

Plan-and-Execute 听起来很稳，但不是所有任务都值得用。

如果任务很短，它会显得啰嗦。

用户问「这个文件里有没有配置项」，你先生成五步计划，就很烦。

如果任务高度依赖实时观察，它也不一定合适。

比如浏览器自动化里点击一个按钮后页面怎么变，下一步必须看结果再决定。

这种场景 ReAct 更自然。

如果计划质量很差，它还会带来一种更隐蔽的问题：

一开始错，后面每一步都看起来很有条理地错下去。

这比无计划乱走还危险。

所以 Plan-and-Execute 最需要防的，不是执行失败。

而是计划看起来很完整，但其实建立在错误假设上。

这也是为什么我觉得它必须配合验证。

每完成一段，都要问：

这一步真的完成了吗？

它是否改变了后续计划？

有没有证据支持继续往下走？

没有这个检查，计划只是漂亮的幻觉。

## 工程上怎么实现

一个最小 Plan-and-Execute 系统，可以分成五块。

第一，Planner。

输入用户目标，输出结构化步骤。

第二，Step Store。

保存计划、每一步状态、执行结果、失败原因。

第三，Executor。

读取当前步骤，调用工具或子 Agent 完成它。

第四，Verifier。

检查这一步是不是真的完成。

第五，Re-planner。

在需要时更新剩余计划。

伪代码大概是：

```
plan = planner.create(user_goal)
while not plan.done():
    step = plan.next_step()
    result = executor.run(step)
    plan.record(step, result)
    if verifier.failed(result):
        plan = replanner.update(plan, result)
return summarize(plan)
```

这里最重要的是状态。

不要只让模型在上下文里记计划。

最好把每一步的状态显式保存下来：

pending、running、done、failed、skipped。

这样才方便恢复、审计、展示进度，也方便用户中途插手。

## 我对 Plan-and-Execute 的理解

如果只用一句话总结：

它让 Agent 在动手之前，先获得一点全局感。

ReAct 像一个会现场排查的人。

Plan-and-Execute 像一个会做项目拆解的人。

前者解决「下一步怎么做」。

后者解决「整件事怎么走」。

真实系统里，两者经常一起出现。

Planner 先拆任务。

Executor 执行每个步骤时，内部再用 ReAct 调工具、查结果、修正动作。

这就比较像人类团队的工作方式了。

先开个短会，把事情拆清楚。

然后每个人去做自己的部分。

做着做着发现计划不对，再回来改计划。

这就是 Plan-and-Execute 的核心。

它不是为了显得 Agent 更严肃。

而是因为复杂任务如果没有地图，很容易把勤奋浪费在错误方向上。
